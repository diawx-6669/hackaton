# Браузерные тесты CampusLens

Юнит-тесты бэкенда (`api/`, pytest) проверяют, что конвейер собирает
правильные данные. Эти тесты проверяют другое: что пользователь видит на
экране. Один раз это уже спасло проект — SSE не доходил до интерфейса,
потому что `sse-starlette` разделяет события через CRLF, а парсер ждал `\n\n`.
Ни один юнит-тест этого не ловил.

## Запуск

```bash
cd web
PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium npm run e2e
```

Переменная нужна только там, где Chromium уже лежит в образе (среда Claude
Code, некоторые CI). На обычной машине достаточно один раз выполнить
`npx playwright install chromium`, и переменную можно не задавать.

Полезное:

```bash
npm run e2e -- --project=chromium     # только десктоп
npm run e2e -- --project=mobile       # только телефон (Pixel 7)
npm run e2e -- e2e/copy.spec.ts       # один файл
npm run e2e -- --headed               # смотреть глазами
npm run e2e:ui                        # интерактивный режим
```

`playwright.config.ts` сам поднимает **продакшен-сборку** на порту 3100
(`next build && next start`), а не dev-сервер: тесты должны проверять то,
что уедет на Vercel.

## Как устроены тесты

Бэкенд в них не участвует. `e2e/fixtures.ts` подменяет все запросы к API
через `page.route()`, включая SSE-поток профиля. Поэтому тесты:

- не зависят от сети, лимитов Wikimedia и доступности Render;
- идут секунды, а не минуты;
- проверяют ровно зону ответственности фронтенда.

Фикстура `mockApi(page, options)`:

- `splitProfile: true` — профиль приходит двумя событиями (`verified` с фото,
  затем `done` с описанием). Так проверяется, что фото показываются
  до того, как ответит LLM;
- `authFails: true` — запросы к `/api/auth/**` обрываются. Так проверяется,
  что недоступный сервер не выдаётся за «вы не вошли».

`signIn(page)` кладёт токен в `localStorage` до загрузки страницы —
форму входа в каждом тесте проходить не нужно.

## Что покрыто

| Файл | О чём |
|------|-------|
| `auth.spec.ts` | гость не видит поиска; вошедший видит; мёртвый бэкенд — это «сервер недоступен», а не «нужен вход» |
| `search.spec.ts` | подсказки вузов: появление, выбор мышью, стрелки и Esc |
| `profile.spec.ts` | все блоки профиля, показ фото до описания, честная пустая категория, источник и лицензия у фото |
| `copy.spec.ts` | тексты, которые мы уже чинили руками |
| `intro.spec.ts` | заставка: показ один раз, пропуск кнопкой и Esc, тишина при reduced-motion, логотип в шапке |
| `mobile.spec.ts` | нет горизонтальной прокрутки на 390 px |

`copy.spec.ts` заслуживает пояснения: каждый тест в нём сторожит решение,
принятое осознанно, — нет пометки «может быть устаревшим», нет эмодзи, нет
сводной оценки безопасности, оценка по прямой подписана как оценка, цена
подана цитатой со ссылкой. Это не украшательство: любое из них легко
вернуть случайной правкой, а все они держат главный принцип проекта —
не выдавать догадку за факт.

## Добавляя тест

1. Данные — в `e2e/fixtures.ts`, не в сам тест: их переиспользуют остальные.
2. Ищите по тому, что видит человек: `getByRole`, `getByText`. CSS-селекторы —
   только там, где семантики нет (`#university`, `#university-hints`).
3. Никаких `waitForTimeout` для ожидания данных: `expect(...).toBeVisible()`
   сам дождётся.
4. Проверяете честность формулировки — пишите тест в `copy.spec.ts`.

## Чего эти тесты не проверяют

Само проигрывание `intro.mp4`: Chromium, который ставит Playwright, собран
без H.264, и `canPlayType('video/mp4; codecs=avc1')` возвращает пустую
строку. Поэтому `intro.spec.ts` проверяет поведение заставки (показ, пропуск,
память о просмотре), а картинку внутри — нет. В Chrome, Safari, Edge и
Firefox у пользователей H.264 есть, но убедиться в этом можно только руками.


Настоящие ответы Wikidata, Commons, Overpass и OSRM — это зона pytest
(`api/tests/`, respx). И реальную вёрстку на боевом домене: моки не поймают
неправильный `CAMPUSLENS_CORS_ORIGINS` на Render. Перед показом жюри всё
равно откройте сайт руками.
